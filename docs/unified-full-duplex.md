# 统一全双工语音会话

2026-11-18，ESP32_VoCatXKorvo。按用户与平台确认实施，沿用 C 服务结构、ESP-IDF 6.1、Opus 与现有 VoCat 音频驱动。

## 当前规则

- 设备待机可预先建立并轻量认证 WebSocket。用户或 MQTT 唤醒后优先复用它进行正式鉴权，也可直接建连。收到 `__proxy_connected__` 后连续上传 AEC 处理过的麦克风音频。见[待机预连接与首句上传](wake-first-phrase.md)。
- 同一连接内 AI 回复、电话和提醒统一接收、解码、播放。16 kHz 单声道，上行 20 ms Opus Base64 JSON，下行一条 binary 消息一个完整 raw Opus 包，未改为 PCM/Ogg。
- 音频收发不依赖 `speech_started` / `speech_stopped` / `response.audio.done` / `response.output_audio.done` / `response.done`。其中平台 `input_audio_buffer.speech_started/stopped` 只参与静默待机，不停止播放、不清缓存。
- 不发送 `response.cancel` / `input_audio_buffer.commit` / `response.create`。平台决定停止生成/发送及提醒优先级；设备不按人声清缓存，平台停发后已有缓存自然播完。
- 无音频只是暂时无输出，仍可继续接新音频。首页轻触结束，或平台未处于用户讲话状态且下行连续安静 30 秒时关闭 WebSocket；平台把关闭视为挂断。MQTT 待机常连。
- 用户主动挂断及真实网络/输出故障仍可清理本次会话缓存，旧连接音频不得进入新连接。

## 有效语音与界面

2026-11-20：静默计时由 `session_policy.h` 统一计算，上行使用平台讲话事件，下行使用 PCM 电平；不以界面的播放状态决定是否计时：

- 上行：收到 `input_audio_buffer.speech_started` 后标记用户正在讲话，取消倒计时；直到收到 `input_audio_buffer.speech_stopped` 才允许重新计时。设备本地麦克风电平/VAD 不再决定待机，AFE/AEC 和连续上传仍照常工作。
- 仅使用上述两个明确的讲话事件；转录 started/completed 不代表实时讲话边界。已认证连接在接收侧立即更新，不排在音频缓存后；序号防止认证期间排队的旧事件反向覆盖。重复 start/stop 不重复重置计时，旧连接事件不影响新会话。
- 下行：成功入队及实际输出的增益前 PCM，按 10 ms 窗口检测平均绝对幅度，至少 64 且连续达到 40 ms 后更新活动时间；静音或分离的短脉冲不续期。阈值集中在 `pcm_policy.h`，不是压缩包大小或语言内容识别。
- 用户未讲话时，从本次会话开始、最近一次 stop、最近一次有效下行音频三者较晚处累计 30 秒。start 清除原倒计时，stop 后重新算完整 30 秒，不恢复旧剩余时间。有效声音入队即续期，缓存尾音播放时继续续期。
- 持续静音包或停止发音频均可超时，无需整个队列排空；心跳、MQTT 状态报告、response/audio.done 等事件不能续期。音量为零不改变下行活动判断。
- 正常静默结束走主动结束流程，清除自动重连意图；不发 cancel，MQTT 不断开。重连/重新唤醒清除旧讲话状态。
- 平台需要在 AI、电话和提醒中可靠发送 start/stop；漏 start 可能误待机，漏 stop 会持续保持讲话状态。用户说完后平台思考/工具等待超过 30 秒仍无声音，也会按规则待机，不隐含增加等待豁免。
- 下行是幅度活动近似，不是语言内容识别；持续背景声音可能保持会话，过弱音频可能未被判为活动，需要实板核对阈值。
- 聆听/播放仅描述界面，切换不启停上传。成功解码并送入播放器的音频保持播放画面；最后入队后至少保持 700 ms，且 PCM/DMA 缓存排空后才回监听。弱音、句间停顿不再按音量阈值切换画面，参数为 `pcm_policy.h` 的 `PCM_UI_HOLD_MS`。
- 持续接收静音音频也显示播放画面，但不刷新上述有效语音计时；用户未讲话时仍可在 30 秒后结束会话。
- 保持现有 UI 的音频优先刷新策略，本次未增加动画负载。

## 播放缓存与退出

PCM 预填 300 ms、容量 500 ms、DMA 约 60 ms；网络消息队列保留既有有界上限。
没有 EOF 的短音频等待不超过 300 ms 即可起播，尾部继续输出，不滞留到下一句话。
缓存全播意味着平台停止发送后可能仍有尾音；实际延迟取决于已接收的网络和 PCM 积压，不能仅以 300 ms 预填估算上限。
超出队列上限的输入记录丢弃诊断，不无限分配内存。

取消旧回复的镜像状态、回合接收门禁、等待回复/播放完成超时与提醒专用播放器生命周期已移除。
保留认证/传输失败恢复、连接代次隔离、分片重组、缓存上限、上传失败检查。
退出先停上传并关闭连接；停止失败则等待清理，不清空仍由上传任务使用的 FIFO，不允许新会话抢用。
真实连接恢复最多等待 60 秒；自动提醒最终失败保留通知，等待用户唤醒、网络恢复或新通知再交接。

## MQTT 提醒

详见 [MQTT 接入](device-mqtt.md)：

1. 待机收到任务：保存编号并唤醒，在正式会话的 auth 中携带 `device_id/api_key/task_ids`。认证后即开始双向音频。
2. 在线收到任务：平台直接推音频；设备不发送额外任务请求、不重复 auth、不重连。
3. 提醒可被平台语音打断，之后保持同一连接继续对话。
4. 设备仅维护待交接通知，不判断完整播报、不发送 `audio_received` 业务回执、不按已播历史去重；MQTT 协议 PUBACK 保留。
5. 保留紧凑 NVS 兼容读取、设备身份隔离和待处理任务 ID，不改分区、不擦除 NVS。

## 回归与实板验收

`python scripts/check_audio.py --cc <TCC路径>` 覆盖生产连续 PCM、上传、WS 分块/鉴权/代次、可选事件后继续收音频、双向静默/时钟回绕、任务唤醒与触屏退出。
`check_device_mqtt.py` 覆盖任务保存/交接/重启/失败暂停；`check_device_auth.py` 和 `check_handshake.py` 覆盖原有凭据流程。

主机测试和编译不能证明真实扬声器听感、AEC 双讲效果与网络稳定性。烧录后至少验证：

1. 无任何 speech/response 事件时，短回复和两分钟以上长音频均可播放。
2. 同时讲话与听对方声音；平台停发时尾音播完，没有 cancel 或事件触发重连。
3. start 后连续讲话超过 30 秒保持连接；stop 后若下行安静满 30 秒退出。倒计时内出现 start 或有效下行声音重新续期；持续静音包及本地噪声不能阻止退出，缓存尾音不能提前截断。
4. 待机提醒唤醒后可说话打断；在线提醒插播不重连，结束后继续对话。
5. 首页在连接、监听、播放阶段轻触均能结束，菜单调节不挂断。
6. 断网/重连、重复任务和重启后无自动唤醒循环；MQTT 始终不发送播放结果 ACK。
